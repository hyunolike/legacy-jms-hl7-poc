## 1. 처리 순서가 설계의 전부다

```
1) 멱등성 선점   ← 가장 먼저
2) PHI 암호화     ← DB 에 닿기 전에
3) DB 적재
4) 병원 B 전달    ← 실패하면 1~3 이 함께 롤백
5) 상태 갱신
```

**선점을 가장 먼저 하는 이유**는 비용 절약이 아니다. 중복 메시지에 SOAP 호출을
태우면 **병원 B 에 같은 입원 통보가 두 번 간다.** 상대 시스템이 멱등하지 않다면
그쪽 데이터가 깨진다. 우리 쪽 중복 방지는 상대 쪽 데이터 보호이기도 하다.

### 선점은 "잠금"이 아니다

이 점을 헷갈리기 쉽다. 선점 INSERT 도 **같은 트랜잭션 안**이라, 4)에서 실패하면
선점도 함께 사라진다. 그래서 재시도가 정상적으로 다시 처리할 수 있다.

만약 선점이 트랜잭션 밖에 있었다면(별도 커밋), 병원 B 전달 실패 → 롤백 → 재전송 →
**"이미 처리됨"으로 판정** → 메시지가 조용히 사라진다. 이건 의료 연동에서 가장
나쁜 실패 모드다. 아무도 모르게 입원 기록이 누락된다.

테스트 두 개가 이 성질을 고정한다.

- `병원B_전달이_실패하면_적재와_선점이_함께_롤백된다`
- `롤백된_뒤_재시도하면_정상_처리된다` ← 앞 테스트의 실질적 의미

선점이 막는 것은 (a) 커밋 이후의 재전송과 (b) 동시에 들어온 같은 메시지, 두 가지다.

### 동시 중복은 DB 가 막는다

`SELECT` 로 먼저 확인하고 없으면 `INSERT` 하는 방식은 두 컨슈머가 동시에 들어오면
둘 다 "없음"을 보고 둘 다 처리한다. 판정을 **DB 의 유니크 제약에 맡기고 영향 행
수로 판단**해야 한다.

```java
return jdbcTemplate.update(SQL_CLAIM, facility, controlId) == 1;
```

PostgreSQL 은 `INSERT ... ON CONFLICT DO NOTHING` 이 충돌하면 앞선 트랜잭션이 끝날
때까지 대기한다. 앞이 커밋되면 이쪽은 0행(중복), 앞이 **롤백되면 이쪽이 1행(최초)**.
즉 "앞이 롤백됐는데 뒤에서 중복으로 판정해 메시지를 잃는" 구멍이 없다.

> **Spring Boot라면**: 동일하다. 멱등성은 프레임워크가 해결해 주지 않는다.

## 2. 리스너의 유일한 책임은 오류 분류다

업무 로직은 서비스가, 파싱은 파서가 한다. 리스너가 정하는 것은 하나뿐이다 —
**롤백해서 재시도할 것인가, 격리하고 커밋할 것인가.**

| 예외 | 동작 | 커밋 | ACK |
|---|---|---|---|
| `Hl7ParseException` | PARK 큐로 격리 | ✅ 커밋 | AR |
| `PermanentProcessingException` | PARK + 격리 기록 | ✅ 커밋 | AE |
| `TransientProcessingException` | 예외 재전파 | ❌ 롤백 | 없음 |
| 그 밖의 `RuntimeException` | 예외 재전파 | ❌ 롤백 | 없음 |

**일시 오류에 ACK 를 보내지 않는 것**이 포인트다. 아직 성공도 실패도 확정되지
않았는데 성급히 AE 를 보내면 송신 측은 "영구 실패"로 처리해 버린다.

**분류되지 않은 예외를 격리하지 않는 것**도 의도다. NPE 같은 것은 버그일 가능성이
높다. 조용히 PARK 로 보내 커밋해 버리면 문제를 못 보고 지나간다. 재시도 → DLQ 로
보내 드러나게 한다.

### 테스트가 잡아낸 실수

처음에는 본문 추출(`extractText`)과 헤더 파싱(`parseHeader`)이 다른 블록에
있었다. 그래서 **본문이 비어 있는 메시지가 격리되지 않고 재시도 4회를 돌다
DLQ 로 갔다.** 빈 본문은 아무리 다시 보내도 빈 본문인데 말이다.

```java
// 고치기 전 — extractText 의 Hl7ParseException 이 catch 범위 밖
final String raw = extractText(message);
try { header = hl7Parser.parseHeader(raw); }
catch (Hl7ParseException e) { handleUnparseable(raw, e); return; }

// 고친 뒤 — 둘 다 "구조를 못 읽었다"로 같이 묶는다
try {
    raw = extractText(message);
    header = hl7Parser.parseHeader(raw);
} catch (Hl7ParseException e) { ... }
```

`본문이_비어_있는_메시지는_한_번만_읽고_분류된다` 테스트가 잡았다.
분기표를 문서로만 적어 두었다면 못 봤을 종류의 어긋남이다.

### 격리 큐 설정이 없으면 메시지를 버리지 않는다

`parkQueue` 가 설정되지 않은 상태에서 격리가 필요하면, 조용히 넘어가지 않고
`TransientProcessingException` 을 던져 롤백한다. 설정 실수로 메시지를 잃는 것보다
DLQ 에 쌓이는 편이 낫다.

## 3. 암호화에서 정한 것

### 암호문 형식 `v1:{keyId}:{IV}:{암호문+태그}`

| 부분 | 없으면 생기는 일 |
|---|---|
| `v1` | 알고리즘을 바꾸려면 전수 재암호화부터 해야 한다. 기존 값이 어느 방식인지 알 수 없으므로 |
| `keyId` | **키 회전 = 데이터 유실.** 과거 암호문을 풀 키를 찾을 수 없다 |

`키를_회전해도_과거_암호문을_읽을_수_있다` 테스트가 이걸 고정한다.

### GCM 을 쓰고 접두부를 AAD 로 묶는다

CBC 는 암호화만 하고 무결성은 보장하지 않는다. DB 가 털린 뒤 암호문 비트를 뒤집는
공격이 통한다. GCM 은 인증 태그로 변조를 탐지한다.

접두부(`v1:keyId`)는 평문으로 노출되므로 **AAD 로 묶어 인증 대상에 포함**시킨다.
묶지 않으면 접두부의 keyId 만 다른 값으로 바꿔치기할 수 있다.
`접두부의_keyId_를_바꿔치기하면_복호화가_실패한다` 가 확인한다.

### IV 는 매 호출 새로 만든다

GCM 에서 같은 키로 IV 를 재사용하면 평문 복원이 가능한 수준으로 무너진다.
상수 IV 는 치명적 결함이다. `같은_평문이라도_매번_다른_암호문이_나온다` 가
100회 암호화해 전부 다른지 본다.

### 블라인드 인덱스는 평문 SHA-256 이 아니라 HMAC 이어야 한다

암호화된 환자 ID 는 IV 때문에 매번 값이 달라 `WHERE` 로 찾을 수 없다. 그래서
결정적인 값을 따로 저장한다.

이때 평문 SHA-256 을 쓰면 **그대로 뚫린다.** `PAT000001` 부터 `PAT999999` 까지
해시를 미리 계산해 두면 끝이다. 값 공간이 좁은 식별자(환자번호, 주민등록번호)는
전수 테이블을 만들 수 있다. 키를 섞은 HMAC 은 키를 모르면 이 계산을 할 수 없다.

**암호화 키와 다른 키를 쓴다.** 하나가 유출돼도 나머지가 남도록.

> ⚠️ 정규화 규칙(공백/대소문자)은 한 번 정하면 바꿀 수 없다. 바꾸면 이미 저장된
> 모든 인덱스가 무효가 되고 과거 데이터는 검색되지 않는다.

### 키가 없으면 기동 자체를 실패시킨다

조용히 뜨면 **첫 환자 메시지가 들어오는 순간에야** 문제를 안다. 그때는 이미 큐에
메시지가 쌓여 있고 DLQ 로 흘러간 뒤다. `InitializingBean` 으로 컨텍스트 로딩
단계에서 막는다.

예외 메시지에는 키 값을 넣지 않는다. 길이만 알려 준다 — 예외는 그대로 로그로 나간다.

### 스레드 세이프

컨슈머가 10개까지 늘어나는 구조다. `Cipher` 와 `Mac` 은 스레드 세이프하지 않으므로
호출마다 새로 만든다. 필드로 공유하면 값이 조용히 섞이고, 재현이 거의 안 된다.

## 4. 순서 역전은 기록하되 버리지 않는다

메시지 그룹으로 순서를 잡아도 컨슈머가 죽어 그룹이 재배정되는 순간에는 흔들린다.
같은 환자의 더 최근 이벤트가 이미 저장돼 있는데 과거 메시지가 도착하면
`OUT_OF_ORDER` 로 기록하고 **처리는 계속한다.**

버리지 않는 이유: 늦게 온 것이 진짜 최신일 수도 있고(송신 측 시계 오차), 의료
데이터를 애플리케이션 판단으로 버리는 쪽이 훨씬 위험하다. 판단 재료를 남기고
사람이 보게 하는 편이 낫다.

## 5. 설계안에서 바꾼 것

**`phiMasker` 빈을 만들지 않았다.** 1단계 설계안에는 있었지만, 주입받아야 할 상태가
없어서 정적 유틸(`MaskingUtils`) + `PatientInfo.toString()` 조합으로 충분하다.
빈으로 만들면 "주입을 깜빡한 곳에서는 마스킹이 안 되는" 경로가 생긴다.

**`AckBuilder` 를 인터페이스로 바꿨다.** 리스너의 관심사는 "무슨 코드로 응답할지"
이지 "ACK 를 어떻게 조립할지"가 아니다. 경계를 먼저 그어 두면 7단계에서 ERR
세그먼트를 붙여도 리스너는 손대지 않는다.

**`AdtEvent` / `PatientInfo` 가 `final` 이라 Mockito 로 mock 할 수 없다.** 불변으로
설계한 대가인데, 값 객체는 실제로 만드는 편이 테스트도 읽기 쉬워서 그대로 뒀다.
